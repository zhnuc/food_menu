# 媒体和读图提速验证 · 2026-10-10

当前模型保持 Gemini 3.8 Flash Low。后端已重启，HTTP接口使用下面的默认配置。

## 保留的改动

- 优先选择平台提供的低清流；无低清流时保留可用视频，下载后缩图不计作减少下载量。
- 小红书复用一次取得的媒体信息下载，图文配图最多4张并行获取。
- FFmpeg一次解码连续抽帧，默认至少3秒一张，长视频约30张；帧长边不超过960像素。
- 每4张原图拼成带ID的2×2拼图，视频单格长边480、图文960像素；每次最多4张拼图，默认3个并发请求，根据任务大小平衡分组。
- 读图仅输出关键原文和简短操作，维持每张原图的证据映射，漏ID、重复ID不视为成功。
- 菜谱返回紧凑字段与食材数组，后端还原原有接口格式，继续验证逐字引用和用量。整理模型不再接收图片。

## 实测

| 样例与条件 | 总耗时 | 说明 |
|---|---:|---|
| 小红书视频，优化前重新下载 | 22.4秒 | before-grid |
| 同一视频，优化后重新下载，两轮 | 14.6 / 12.8秒 | 3秒采样，所有阶段重新执行，无缺帧警告 |
| 同一视频，实际HTTP接口，媒体已缓存，重新抽帧、识别、整理 | 10.3秒 | 端到端墙钟时间；后端自身10.1秒 |
| 同一视频，实际HTTP接口再次生成 | 0.6秒 | 复用识别和菜谱缓存 |
| 抖音图文12道菜，优化前 | 46.0秒 | 媒体已缓存，读图和整理重跑 |
| 同一图文，优化后最终配置 | 22.4秒 | 同样缓存条件，完整12道菜 |
| B站视频，最终配置首次下载 | 18.3秒 | 无缺帧警告，完整1道菜 |

时长受网络和模型服务影响，不能保证任意链接首次处理固定10秒。不同缓存条件分开记录，以上不混用。

## 内容核对

HTTP生成的小红书菜谱核对了12项关键用量：生菜200克、面粉250克、水120克、鸡蛋1颗、淀粉水1勺、生抽1勺、陈醋1勺、香油1勺、辣椒油1/2勺、白胡椒1/4勺、虾皮1勺、紫菜3克；静置20分钟、煮2分钟保留。16项检查包括无识别警告和购物接口，全部通过，见 optimized-quality-check.json。

36项单元检查通过，覆盖拼图比例、原图顺序、16张原图与尾图的映射、缺ID重试、单次解码抽帧与颜色顺序、缓存失效、紧凑菜谱还原及用量校验。

## 未采用的试验

- 4秒采样虽然12.5秒，但漏掉鸡蛋与淀粉水字幕，保持默认3秒。
- 一轮640像素拼图有一批读图请求超时，整次82.4秒且缺4帧；不算作成功提速。失败记录保留为 speed-grid640-balanced.json。
